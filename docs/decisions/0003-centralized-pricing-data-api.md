# ADR 0003: All third-party pricing data goes through one internal API

**Status:** Accepted · **Date:** 2026-06

## Context

CounterMint depends on several external providers: spot prices for four metals, sold-comparable listings, and published sheet pricing. Several internal services need those values — the quote service, the valuation engine, the appraisal pipeline, document generation.

The path of least resistance is for each service to call the provider it needs. It works immediately and it is what most codebases end up doing.

Three problems with it. Provider calls are metered and expensive, so N services calling the same endpoint means paying N times for one value. Provider contracts change, and when they do the fix is spread across every call site. And cost becomes unobservable — with calls scattered, nobody can answer what a given tenant costs in third-party data.

## Decision

Every provider call goes through a single internal data API. No service talks to a provider directly.

That layer owns caching, request deduplication and rate control. One adapter exists per provider, so a contract change is one fix. Values are normalized on arrival and stored once, and every internal consumer reads the normalized record rather than a provider response.

Spot refreshes on a sixty-second cycle; the normalized store is the single source of truth that every client surface reads. Dealer and client documents refresh from that store automatically rather than being regenerated by hand.

## Consequences

**Good.** Provider spend is bounded by refresh cadence rather than by internal call volume, so it does not scale with traffic. Cost is observable at one point, which is the only reason it is controllable. A provider outage degrades to serving cached values instead of failing every dependent path. No two client surfaces can disagree about today's spot, because there is only one number.

**Bad.** The data API is a single point of failure and needs to be correspondingly reliable. Cache invalidation is now a real design problem with real staleness tradeoffs. There is indirection between a service and the data it needs, which costs something in debuggability.

**Neutral.** This is what made adding the CDN/Greysheet client straightforward — it is another adapter behind the same interface rather than a new integration pattern. Commercial access is still under negotiation; the client, GSID resolution and fixtures are complete and tested against recorded responses.

## What I would revisit

Refresh cadence is currently uniform. Spot genuinely needs sixty seconds; sold comparables almost certainly do not, and sheet pricing updates on a publication schedule measured in days. Per-provider cadence would cut spend further and is not yet implemented.
